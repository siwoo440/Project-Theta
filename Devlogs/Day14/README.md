# Project θ 개발 일지 — 14일차

## 개발 목표

13일차에 세이브 파일을 만들었지만 그 안은 "빈 지갑"이었다. 기록은 남되 그 기록이 아무것도 바꾸지 않았다.

14일차는 밀린 정리 작업까지 함께 당겨 7개 묶음을 처리했다.

```text
A. 데이터 ScriptableObject 자산화
B. 계약 정기 환산
C. 4계열 × 5단계 영구 성장

E. 난이도 3종 프리셋

G. 2D 캐릭터 표현 기반 + 튜토리얼 트리거 골격
```

## 문제 인식

두 가지였다.

**플레이가 쌓이지 않았다.** 13일차 세이브에서 실제로 채워지는 건 클리어 횟수·최고 점수·최고 랭크뿐이었고, `ContractEssence`와 `UpgradeLevels`는 빈 칸이었다. S 랭크를 받아도 다음 판이 똑같았다.

**밸런스 숫자가 전부 코드에 박혀 있었다.** 10~13일차 개발일지마다 "실제 플레이 데이터를 보고 조정할 임시값"이라고 적어둔 항목이 8개 표에 걸쳐 쌓여 있었고, 하나 바꾸려면 코드 수정과 재컴파일이 필요했다.

# A. 데이터 ScriptableObject 자산화

## 핵심 원칙 — 계산식은 코드, 숫자만 자산

이 원칙을 지킨 이유는 분명하다.

현재 EditMode 테스트 197개는 **Unity 자산이나 `Resources.Load` 없이** 돈다. 계산식을 자산으로 옮기면 이 테스트가 전부 못 돌게 된다.

그래서 각 로직 클래스의 계산 방식은 그대로 두고, 숫자만 `StageBalanceValues`로 뺐다.

## 주입 구조

```text
자산 없음  →  코드 안의 기본 표 사용   (테스트 환경이 항상 이 경로)
자산 있음  →  자산 값으로 덮어씀       (실행 환경)
```

각 표에 `Override` 주입 지점을 만들고, 비어 있으면 기존 정적 표를 그대로 쓴다.

```csharp
private static NpcGradeProfile[] Active =>
    Override != null && Override.Length > 0
        ? Override
        : Profiles;
```

`BalanceBootstrap`이 `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`에서 자산을 읽어 주입한다. **자산 로딩이 실패해도 게임은 그대로 동작한다.**

## 자산으로 뺀 수치

| 자산 | 내용 |
| --- | --- |
| `NpcDatabase.asset` | 5등급 수치, 6특성 보정 |
| `StageBalanceDatabase.asset` | 랭크 구간, 콤보, 회수 배율, 파동, 체인, 계약 정기 환산, 경쟁자 튜닝 2종, 소비 아이템 4종, 난이도 3종 |

두 자산은 `Assets/_Project/Resources/Balance/`에 두었고, 값은 현재 코드 기본값과 완전히 동일하게 생성했다. 따라서 자산 도입만으로는 게임 동작이 전혀 바뀌지 않는다.

## const에서 프로퍼티로

`StageRankLogic.BThreshold` 같은 `const`는 자산으로 덮을 수 없으므로 정적 프로퍼티로 바꿨다. 기존 값은 `DefaultBThreshold`로 남겨 대조용으로 쓴다.

구조적 상한은 `const`로 유지했다.

```text
ChainHypnosisLogic.MaximumChain = 3      구조적 상한, 조정 대상 아님
ComboLogic.MinimumMultiplier = 1.0       기준값, 조정 대상 아님
```

반대로 `ComboLogic.MaximumCombo`는 상수에서 **역산 프로퍼티**로 바꿨다. 단계 배율과 상한이 자산에서 바뀌면 자동으로 따라와야 하기 때문이다.

```csharp
MaximumCombo = (MaximumMultiplier - MinimumMultiplier) / StepMultiplier
```

기획서 10.1절·13.3절. 스테이지 내부 정기와 영구 재화를 분리했다.

| 요소 | 계수 |
| --- | ---: |
| 회수 확정 정기 | × 0.5 |
| 랭크 보너스 | C 0 / B +20 / A +50 / S +100 |

## 실패해도 절반은 준다

기획서 24장 "이미 확정 회수한 정기의 일부는 보존해 반복 실패의 피로도를 줄인다"를 그대로 구현했다.

```text

클리어 →  회수분 × 0.5 + 랭크 보너스 + 초과분 × 0.3
```

11일차에 `StageScoreTracker.RecoveredEssence`를 **목표치에 캡되지 않은 실제 회수량**으로 만들어 둔 덕분에 초과분 계산이 바로 됐다. (`StageSessionController.CurrentEssence`는 목표치에서 잘린다.)

# C. 4계열 영구 성장

기획서 14장. 각 계열 5단계다.

| 계열 | 단계당 효과 | 5단계 누적 |
| --- | --- | --- |
| 최면 | 최면 속도 +6% | +30% |
| 관리 | 안정 관리 한도 +1, 유지도 감소 −7% | 4명 → 8명, −35% |
| 안정 | 충동 상승 −8%, 폭주 경고 +0.1초 | −40%, +0.5초 |
| 기동 | 이동 속도 +4%, 대시 집중력 −10% | +20%, −50% |

누진 비용이다.

| 레벨 | 1 | 2 | 3 | 4 | 5 | 계열 총합 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 비용 | 40 | 70 | 110 | 160 | 220 | **600** |

전 계열 만렙은 2,400 계약 정기다.

## 주입 방식

`PlayerUpgrades`가 세이브의 레벨과 현재 난이도를 읽어 **최종 배율 하나**로 합친다.

각 시스템은 자기가 성장했는지·난이도가 무엇인지 알 필요가 없다.

```text
HypnosisTarget.BuildPerSecond  ×= PlayerUpgradeMultipliers.HypnosisSpeed
ImpulseMeter 충동 상승          ×= PlayerUpgradeMultipliers.ImpulseBuild
PlayerSideViewController 속도   ×= PlayerUpgradeMultipliers.MoveSpeed
PlayerFocus 대시 비용           ×= PlayerUpgradeMultipliers.DashCost
StageSessionController 목표·시간 ×= 난이도 배율
```

NPC처럼 플레이어를 직접 참조하지 않는 컴포넌트가 매 프레임 탐색하지 않도록, `PlayerUpgrades`가 `Awake`에서 `PlayerUpgradeMultipliers.Active`에 자신을 등록하고 `OnDestroy`에서 해제한다.

플레이어가 없는 상황(타이틀 화면·테스트)에서는 난이도 배율만 적용되고 성장 배율은 1.0이 된다.

# F. 사운드 매니저

밀린 중복 정리다.

9일차 인기남 선점 효과음과 11일차 결과 화면 효과음이 **거의 동일한 클립 생성 코드를 각자 갖고 있었다.** 11일차 개발일지에 "이후 정리 대상으로 남겨둔다"고 적어둔 부분이다.

```text
PopularGuyController.CreateClaimTickClip()   약 60줄
RuntimeUiSfx.CreateTone()                    약 60줄
        ↓
RuntimeToneFactory.CreateTone()              하나로 통합
GameAudio.Play(GameSfx)                      재생 창구 단일화
```

`RuntimeUiSfx`는 삭제했다.

## 정식 사운드 교체 경로

`GameAudio`는 먼저 `Resources/Audio/<효과음 이름>`을 찾고, 없으면 런타임 합성음으로 대체한다.

```text
오디오 파일 있음  →  그 파일 재생
오디오 파일 없음  →  런타임 단음 생성 (현재)
```

정식 사운드가 준비되면 **파일만 넣으면 되고 호출부는 전부 그대로**다.

# G. 2D 캐릭터 표현 기반 + 튜토리얼 골격

## 정렬 규칙 정리

기존 `DepthSortByY`는 `_baseOrder = 1000`, `_unitsToOrder = 100` 같은 값을 컴포넌트마다 들고 있었다. 이를 공용 규칙으로 옮겼다.

```text
Background        0 ~  9999
Character     10000 ~ 19999   ← Y 좌표로 서로 앞뒤 결정
CharacterOverlay 20000 ~ 29999   머리 위 게이지·아이콘
ScreenUi      30000 ~ 39999
```

계층마다 정렬 구간을 나눠서, **캐릭터가 아무리 아래에 있어도 머리 위 UI나 화면 UI를 가리지 않는다.** 기존 구조에서는 Y가 충분히 작으면 이론적으로 겹칠 수 있었다.

깊이 변위는 계층 폭 안으로 Clamp한다.

## 튜토리얼 트리거 골격

기획서 A.11절의 단계 개방 순서를 규칙으로만 정의했다.

```text
최면 → 동행 → 회수 → 쟁탈 → 폭주 → 완료
```

각 단계의 통과 조건과 안내 문구를 `TutorialFlowLogic`에 두었다. **실제 배치는 아카데미 구역 작업**이므로 지금은 시스템만 준비한 상태다.

여러 단계를 한 번에 건너뛸 수 있게 만들었다. 숙련된 플레이어가 첫 구역에서 이미 쟁탈까지 경험했다면 안내를 하나씩 띄울 이유가 없다.

# 14일차 결과

14일차를 기준으로 이 게임에 처음으로 **"다음 판을 할 이유"** 가 생겼다.

한 판의 결과가 계약 정기로 남고, 그 정기로 산 성장이 다음 판을 실제로 바꾼다. 랭크가 처음으로 점수판 이상의 의미를 갖게 됐다 — S와 C의 계약 정기 차이가 100이다.

개발 쪽에서는 8개 표에 흩어져 있던 밸런스 수치가 자산 2개로 모였다. 28일차 전체 밸런스 패스에서 수십 번 반복할 조정 작업이 이제 인스펙터에서 끝난다.

## 남은 확인 사항

계약 정기 환산 계수(×0.5), 성장 비용(계열당 600), 난이도 배율은 모두 계산상의 추정값이다.

한 판에 들어오는 계약 정기가 80~150 정도일 것으로 보고 전 계열 만렙을 20판 안팎으로 잡았는데, 이는 기획서 A.1의 "첫 엔딩 3~5시간"과 대략 맞춘 수치다. 실제 플레이 데이터가 나오면 자산에서 조정한다.
