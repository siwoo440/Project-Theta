# Project θ 개발 일지 — 10일차

## 개발 목표

9일차까지 Player·금태양·인기남의 다세력 경쟁 구조와 힘겨루기를 완성했다.

10일차는 다음을 처리했다.

```text
A. 경쟁자 AI 공통 베이스 추출 (동작 변경 없는 리팩터링)
B. NPC 등급 시스템 (일반 / 숙련 / 희귀 / 특수 / 각성)
C. NPC 특성 시스템 (일반형 포함 5종)
```

리팩터링을 먼저 한 이유는, 등급·특성을 고려한 타겟 평가 로직을 금태양과 인기남 양쪽에 중복해서 넣지 않기 위해서다.

# A. 경쟁자 AI 공통 베이스 추출

## 문제

9일차까지 금태양과 인기남은 서로 다른 클래스였지만 내용은 거의 같았다.

| 파일 | 줄 수 |
| --- | ---: |
| `RivalController` (금태양) | 632 |
| `PopularGuyController` (인기남) | 963 |

두 클래스가 `Awake / Configure / Update / FixedUpdate / SetDuelLocked / ApplyDuelStun / ReleaseOwnedTarget / UpdateTargetSearch / IsTargetValid / ClearTarget / UpdateIdle / EnterIdle / FaceHorizontal / StopMovement / OnDisable` 15개 멤버를 거의 동일하게 중복 보유했다.

Follower 시스템도 마찬가지였다.

```text
RivalFollowerManager       178줄
PopularGuyFollowerManager  179줄   ← 이름만 다르고 내용 동일
RivalFollowerController    157줄
PopularGuyFollowerController 157줄 ← 이름만 다르고 내용 동일
```

이 상태에서 특성·등급을 추가하면 같은 코드를 두 번 수정해야 하고, 기획서 A.7의 경쟁자 3종(유혹형/방해형/각성형)으로 확장하면 세 벌이 된다.

## 구조 변경

```text
OpponentControllerBase (공통)
├─ 상태 머신 Idle / Search / Approach / Claiming / Contest / Stunned
├─ 이동, 방향 전환, 정지
├─ Idle 랜덤 대기
├─ 타겟 유효성 판정 및 추적 포기
├─ 힘겨루기 잠금 / 기절 처리
├─ 소유권 전환 공통 경로 (충동 정리 → 플레이어 Follower 분리)
└─ 확보 성공 후 Idle 복귀

  ├─ GeumtaeyangController : Player 동행 NPC 평가 후 쟁탈
  └─ PopularGuyController  : Neutral 3단계 선점 우선, 없으면 쟁탈
```

파생 클래스가 구현하는 것은 다음 네 가지뿐이다.

```text
CreateDefaultTuning()   자기 행동 수치
SearchForTarget()       누구를 노릴지
IsTargetValid()         그 대상이 아직 유효한지
PerformAction()         어떻게 확보할지
```

## 수치 분리

경쟁자별 차이를 `OpponentTuning` 한 곳에 모았다.

| 항목 | 금태양 | 인기남 |
| --- | ---: | ---: |
| 이동 속도 | 4.2 | 2.1 |
| 재탐색 주기 | 0.30초 | 0.90초 |
| 쟁탈 지배 감소 | 18 / sec | 12 / sec |
| 최대 추적 시간 | 5.0초 | 7.5초 |
| 시작 Idle | 0.6~1.5초 | 1.8~4.5초 |
| 타겟 상실 Idle | 0.4~0.9초 | 1.2~2.7초 |
| 확보 후 Idle | 0.5~1.2초 | 1.5~3.6초 |

## Unity 직렬화 관련 수정

처음에는 `_tuning`이 null일 때만 기본값을 채우도록 작성했다.

그러나 Unity는 직렬화된 사용자 클래스 필드를 기본 생성 인스턴스로 채울 수 있어, null 검사가 통과되지 않고 인기남이 금태양 수치를 그대로 사용할 위험이 있었다.

따라서 `Awake`에서 항상 파생 클래스의 수치로 초기화하도록 변경했다.

## Follower 시스템 통합

```text
RivalFollowerManager / PopularGuyFollowerManager
→ OpponentFollowerManager

RivalFollowerController / PopularGuyFollowerController
→ OpponentFollowerController
```

소유자 구분은 같은 오브젝트의 `OwnerTag`로 처리하므로 경쟁자가 늘어나도 Follower 코드는 그대로 재사용한다.

## 소유자 API 단일화

`HypnosisTarget`이 경쟁자별로 따로 들고 있던 참조와 메서드를 하나로 합쳤다.

```text
GeumtaeyangOwner / PopularGuyOwner
→ OpponentOwner

ClaimByGeumtaeyang() / ClaimByPopularGuy()
→ ClaimByOpponent()

ApplyGeumtaeyangPressure() / ApplyPopularGuyPressure()
→ ApplyOpponentPressure(attacker, ...)
```

쟁탈 가능 판정도 `OwnershipContestLogic.CanContest(attacker, owner)` 한 곳으로 모았다.

이 덕분에 플레이어의 재탈환 처리도 다음과 같이 단순해졌다.

```text
기존: Owner가 금태양이면 ... else 인기남이면 ...
변경: target.OpponentOwner?.ReleaseOwnedTarget(target)
```

## 이름 정리

게임 내 명칭과 코드 명칭을 맞췄다.

```text
RivalController          → GeumtaeyangController
RivalState               → OpponentState
RivalIdleLogic           → OpponentIdleLogic
RivalTargetDecisionLogic → OpponentTargetDecisionLogic
PopularGuyState          → OpponentState (통합)
PopularGuyTargetMode     → OpponentTargetMode
```

네임스페이스 `ProjectTheta.Rival`은 "경쟁자 세력 전반"을 뜻하므로 유지했다.

## 리팩터링 결과

| 구분 | 기존 | 변경 후 |
| --- | ---: | ---: |
| 경쟁자 관련 코드 합계 | 2,522줄 | 1,923줄 |

단순 줄 수보다 중요한 것은, 경쟁자 1종을 추가할 때 필요한 코드가 약 900줄에서 약 150줄로 줄었다는 점이다.

이 단계는 동작 변경이 목적이 아니므로 기존 EditMode 테스트가 그대로 통과하는 것을 완료 기준으로 삼았다.

# B. NPC 등급 시스템

## 문제

9일차까지 테스트 스테이지의 NPC 10명은 위치만 다를 뿐 완전히 동일했다.

```text
최면 속도  32 / sec  (전원 동일)
정기 보상  5         (전원 동일)
충동 상승  동일
```

누구를 먼저 노릴 이유가 없어서 가장 가까운 NPC부터 집는 것이 항상 최적이었다.

## 5등급 정의

기획서 15장·20장을 기준으로 등급별 수치를 정의했다.

| 등급 | 최면 속도 | 최면 시간 | 정기 가치 | 충동 배율 |
| --- | ---: | ---: | ---: | ---: |
| 일반 | 40 / sec | 2.5초 | 10 | 1.00 |
| 숙련 | 24 / sec | 4.2초 | 20 | 1.10 |
| 희귀 | 14 / sec | 7.1초 | 40 | 1.25 |
| 특수 | 12 / sec | 8.3초 | 60 | 1.30 |
| 각성 | 8 / sec | 12.5초 | 50 | 1.15 |

최면 시간은 기획서 20장의 초기안(일반 2.0\~3.0초 / 숙련 3.5\~5.0초 / 희귀 6.0\~9.0초) 범위 안에 들어가도록 맞췄고, 이를 테스트로 고정했다.

## 정기 가치 연동

현재 스테이지는 회수 보상과 동행 중 패시브 생산을 함께 사용한다.

기획서의 절대 수치(10 / 20 / 40)를 그대로 보상으로 쓰면 기존 밸런스가 무너지므로, **일반 등급을 1.0으로 본 배율**로 환산해 기존 보상에 곱하는 방식을 사용했다.

```text
회수 보상 = 기본 회수 보상 × 등급 배율
패시브    = 기본 패시브     × 등급 배율

일반 1.0 / 숙련 2.0 / 희귀 4.0 / 각성 5.0 / 특수 6.0
```

`StageRules.ScaleEssenceReward`로 분리해 테스트 가능하게 만들었고, 기본 보상이 0보다 크면 결과가 최소 1이 되도록 해 저배율에서 보상이 사라지지 않게 했다.

회수 지점 확정형 정기 구조로의 전환 자체는 11일차 목표·점수·콤보 작업으로 넘긴다.

## 프로토타입 스테이지 구성

테스트 스테이지 NPC 10명을 다음과 같이 배치했다.

```text
일반 5 / 숙련 3 / 희귀 1 / 각성 1
```

특수 등급은 선행 조건 시스템이 필요하므로 데이터 구조만 정의하고 배치하지 않았다.

## 등급 표시

NPC 머리 위 왼쪽에 등급 색상 표식을 추가했다.

```text
일반  회백색
숙련  하늘색
희귀  보라색
특수  금색
각성  주황빨강
```

# C. NPC 특성 시스템

## 특성 5종

기획서 5.4절의 저항 패턴을 특성으로 옮겼다.

| 특성 | 동작 | 최면 속도 | 정기 가치 |
| --- | --- | ---: | ---: |
| 일반형 | 특별한 저항 없음. 그냥 평범하게 최면당한다 | ×1.00 | ×1.00 |
| 시선 회피형 | 주기적으로 고개를 돌려 최면 게이지 상승을 멈춘다 | ×1.00 | ×1.10 |
| 도주형 | 최면 대상이 되면 플레이어 반대 방향으로 달아난다 | ×1.00 | ×1.15 |
| 고저항형 | 최면이 느린 대신 정기 가치가 높다 | ×0.60 | ×1.50 |
| 각성 지원형 | 주변 플레이어 동행 NPC의 지배 수치를 깎는다 | ×0.85 | ×1.30 |

여러 특성을 가지면 배율은 곱해서 적용한다.

### 보류한 2종

- **반격형** — 플레이어 집중력을 깎는 특성인데 집중력 자원이 아직 없다. 12일차 최면 확장에서 함께 추가한다.
- **경비 호출형** — 방해 NPC 스폰 시스템이 필요하다. 구역 콘텐츠 단계로 넘긴다.

## 일반형의 의미

일반형은 "특성 없음"을 나타내는 명시적인 값이다.

다른 특성이 하나라도 붙으면 일반형은 목록에서 제거되고, 남는 특성이 없을 때만 일반형 하나가 남는다.

```text
일반형 + 도주형  → 도주형
일반형 + 일반형  → 일반형   ← 진짜 평범한 NPC
```

이 규칙 덕분에 일반 등급 NPC의 약 절반은 아무 저항 없이 그대로 최면당하는 개체가 된다.

## 특성 부여 규칙

기획서 A.5의 "핵심 특성은 유형별로 고정하고 재도전 시 보조 특성 1개를 무작위로 부여" 규칙을 그대로 구현했다.

| 등급 | 고정 특성 | 보조 특성 풀 |
| --- | --- | --- |
| 일반 | 일반형 | 일반형, 일반형, 시선 회피형, 도주형 |
| 숙련 | 시선 회피형 | 일반형, 도주형, 고저항형 |
| 희귀 | 시선 회피형, 고저항형 | 일반형, 도주형 |
| 특수 | 고저항형, 도주형 | 일반형, 시선 회피형 |
| 각성 | 각성 지원형, 고저항형 | 일반형 |

따라서 같은 NPC라도 재시작하면 보조 특성이 달라진다.

## 시선 회피형 구현

주기 2.4초 중 앞 0.9초 동안 최면 게이지 상승을 차단한다.

```text
0.0 ────── 0.9 ────────────── 2.4
   차단          정상 상승
```

같은 프레임에 모든 회피형이 동시에 고개를 돌리지 않도록 시작 위상을 무작위로 흩뿌렸다.

차단은 중립 NPC의 최면 축적에만 적용하고, 경쟁자에게서 되찾는 재탈환에는 적용하지 않는다.

## 도주형 구현

플레이어의 최면 대상으로 지정되고 아직 중립이면 도주를 시작한다.

```text
최면 대상 지정
↓
플레이어 반대 방향으로 목표 지점 재설정 (0.45초 주기)
↓
이동 속도 ×1.45
```

목표 지점은 복도 이동 가능 범위 안으로 제한해 벽으로 파고들지 않게 했다.

## 각성 지원형 구현

반경 3.2 안의 플레이어 동행 NPC의 지배 수치를 초당 6씩 깎는다.

```text
각성 NPC 반경 진입
↓
동행 NPC 지배 수치 감소
↓
0 도달
↓
무리에서 이탈, 중립 복귀
```

각성 NPC 본인이 최면당하면 오라도 멈춘다.

대상 검색은 매 프레임이 아니라 0.25초 주기로 수행하고, 그 사이에는 캐시된 목록만 갱신한다.

## 특성 표시

등급 표식 아래에 보유 특성 수만큼 작은 색상 핍을 세로로 배치했다.

일반형만 가진 NPC에는 핍을 표시하지 않아, 화면에서 바로 "평범한 NPC"를 구분할 수 있다.

## Debug HUD

`Day 10 Debug`로 갱신하고 현재 최면 대상의 등급·특성·상태를 표시한다.

```text
최면 대상: FemaleNPC_05 [희귀]
Move(도주) / 최면 42% / 시선 회피형 · 고저항형
```

도주 중이거나 시선이 끊긴 상태도 함께 표시해 특성이 실제로 작동하는지 바로 확인할 수 있다.

# D. 군중 뭉침 개선과 방황 이동

## 문제

동행 인원이 늘어나는 후반부에 캐릭터들이 한 덩어리로 뭉쳐 다니는 문제가 있었다.

원인은 세 가지였다.

```text
1. 플레이어 동행의 방황 진폭이 0.08 / 0.11로 거의 없는 수준
2. 경쟁자 동행에는 방황이 아예 없어 격자 대열로 고정
3. 중립 NPC는 Idle 상태에서 완전히 정지
```

특히 2번 때문에 금태양·인기남이 NPC를 많이 확보할수록 직사각형 블록처럼 보였다.

## 공용 방황 시스템

모든 캐릭터가 같은 방황 성분을 쓰도록 공용 구조를 만들었다.

```text
NpcWanderLogic    순수 계산 (서로 다른 두 주파수를 겹친 오프셋)
NpcWanderMotion   개체별 위상·속도·진폭을 들고 있는 컴포넌트
```

단순 사인 곡선 하나만 쓰면 모든 캐릭터가 같은 원을 그려 오히려 더 뭉쳐 보인다.

따라서 주파수가 다른 두 파형을 0.66 : 0.34로 겹쳐 리사주 곡선 형태를 만들고, 개체마다 위상·속도·진폭을 무작위로 부여했다.

진폭 계수의 합이 1이므로 오프셋은 항상 지정한 진폭 안에 머문다.

| 항목 | 값 |
| --- | ---: |
| 기본 수평 진폭 | 0.46 |
| 기본 수직 진폭 | 0.38 |
| 방황 속도 | 0.42 ~ 1.05 |
| 개체별 진폭 편차 | ±35% |

## 적용 범위

세 곳 모두에 같은 방황을 적용했다.

| 대상 | 변경 |
| --- | --- |
| 중립 NPC | Idle·Alert에서 기준점 주변을 천천히 서성임 (기존: 완전 정지) |
| 플레이어 동행 | 대열 오프셋 + 방황 (진폭 0.08/0.11 → 0.46/0.38) |
| 경쟁자 동행 | 대열 오프셋 + 방황 신규 적용 |

최면된 NPC도 대상에 포함되므로, 플레이어를 따라다니는 무리와 경쟁자에게 끌려간 무리 모두 느슨하게 움직인다.

Alert 상태에서는 진폭을 35%로 줄여 플레이어를 의식하고 멈춰 서는 느낌은 유지했다.

## 대열 자체를 느슨하게

방황만으로는 부족해 대열 배치값도 함께 풀었다.

| 항목 | 기존 | 변경 |
| --- | ---: | ---: |
| 수평 개인 오프셋 | ±0.38 | ±0.62 |
| 수직 개인 오프셋 | ±0.42 | ±0.58 |
| 추종 속도 편차 | ±10% | ±18% |
| 정지 거리 편차 | 0 ~ 0.10 | 0 ~ 0.22 |

경쟁자 동행에는 이 개인 오프셋 자체가 없었으므로 새로 추가했다.

소유권이 바뀌어 다른 무리로 옮겨갈 때마다 위상·오프셋을 다시 뽑으므로 대열이 매번 새로 흐트러진다.

## 소프트 분리 강화

서로 밀어내는 거리도 함께 올렸다.

| 항목 | 기존 | 변경 |
| --- | ---: | ---: |
| 유지 희망 거리 | 0.65 | 0.88 |
| 최대 밀어내기 속도 | 0.9 | 1.20 |

## 추종 속도 감소

동행 NPC가 플레이어에게 딱 붙어 따라오지 않도록 추종 속도를 기존 수치의 1/3만큼 낮췄다.

| 대상 | 항목 | 기존 | 변경 |
| --- | --- | ---: | ---: |
| 플레이어 동행 | 기본 추종 | 5.00 | 3.33 |
| 플레이어 동행 | 따라잡기 | 7.00 | 4.67 |
| 경쟁자 동행 | 기본 추종 | 4.80 | 3.20 |
| 경쟁자 동행 | 따라잡기 | 6.60 | 4.40 |

추종이 느려지면서 무리가 플레이어 뒤로 자연스럽게 늘어지고, 이동 중 대열이 길어졌다 모였다 하는 움직임이 생긴다.

동시에 거리 유지도 감소와 이탈 위험이 실제 압박으로 작동하기 시작한다.

## 중립 NPC Idle 시간 단축

제자리 서성임이 추가되었으므로 Idle 유지 시간도 줄여 전체 움직임을 늘렸다.

```text
0.8 ~ 2.2초
→ 0.55 ~ 1.60초
```

# 테스트

이번 일차에 추가·갱신한 EditMode 테스트는 다음과 같다.

`NpcGradeTableTests`

- 5등급이 모두 정의되어 있는지
- 등급이 높을수록 최면이 느려지는지
- 최면 시간이 기획서 20장 범위 안에 있는지
- 정기 가치가 기획서 값(10 / 20 / 40)과 일치하는지
- 일반 등급이 정기 배율 1.0 기준인지
- 정의되지 않은 등급이 안전하게 대체되는지

`NpcTraitAssignmentLogicTests`

- 일반 등급이 실제로 완전한 일반형 NPC를 만들 수 있는지
- 다른 특성이 붙으면 일반형이 제거되는지
- 고정 특성이 난수와 무관하게 항상 붙는지
- 각성이 항상 각성 지원형을 가지는지
- 특성이 중복되지 않는지
- 난수 범위 밖 입력이 Clamp되는지
- 보조 특성이 난수에 따라 실제로 달라지는지

`NpcTraitEffectTests`

- 일반형이 아무 수치도 바꾸지 않는지
- 고저항형의 ×0.60 / ×1.50 보정
- 여러 특성의 배율이 곱해지는지
- 빈 목록·null이 안전한지
- 모든 특성에 프로필이 있는지
- 시선 회피 차단 구간과 주기 반복
- 등급과 특성을 합친 최종 결과가 일반 NPC보다 느리고 값비싼지

`NpcWanderLogicTests`

- 오프셋이 지정한 진폭을 넘지 않는지
- 위상이 다르면 결과가 달라지는지 (무리가 같이 흔들리지 않는지)
- 속도가 다르면 시간이 지나며 벌어지는지
- 작은 시간 간격에서 튀지 않고 연속적인지
- 진폭이 있는데도 중심에만 머물지 않는지
- 진폭 0이면 오프셋이 0인지
- 음수 시간이 0으로 Clamp되는지

`StageRulesTests` (추가)

- 등급 배율이 회수 보상에 적용되는지
- 기본 보상이 양수면 최소 1을 보장하는지
- 기본 보상이 0이면 0을 유지하는지

기존 테스트는 이름만 바뀌어 그대로 유지했다.

```text
RivalIdleLogicTests           → OpponentIdleLogicTests
RivalTargetDecisionLogicTests → OpponentTargetDecisionLogicTests
```

특히 `OpponentTargetDecisionLogicTests`는 8일차의 "타겟 없이 Idle만 반복하던 버그"에 대한 회귀 테스트이며, 공통 베이스로 옮긴 뒤에도 같은 경로를 사용하도록 유지했다.

## 10일차 결과

10일차를 기준으로 NPC가 처음으로 "서로 다른 공략 대상"이 되었다.

이전까지는 가장 가까운 NPC부터 집는 것이 항상 최적이었지만, 이제는 느리지만 값비싼 고저항형을 노릴지, 빠르게 회전하는 일반형으로 콤보를 유지할지, 각성 NPC를 피해 동선을 짤지를 판단해야 한다.

동시에 경쟁자 AI가 공통 베이스 위에 올라가면서, 이후 경쟁자 유형 추가와 특성·등급을 반영한 타겟 평가 확장이 한 곳의 수정으로 끝나는 구조가 되었다.
