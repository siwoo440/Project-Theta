# 16일차 - 층 구조 및 계단 이동·동행 인계 구현

## 이번 일차의 목표

지금까지 한 판은 **복도 하나**에서 시작해서 복도 하나에서 끝났다.

16일차는 이것을 **여러 층으로 이뤄진 건물**로 바꾼다.

- 각 층 벽면에 계단이 있다
- 계단 앞에 서면 위층·아래층으로 이동할 수 있다
- **최면으로 동행 중인 캐릭터가 함께 따라온다**

원래 계획은 "구역을 한 방향으로 넘어가는" 구조였다.
이를 **오르내릴 수 있는 층**으로 바꾸었다. 되돌아갈 수 있다는 점이 가장 큰 차이다.

---

## A. 핵심 결정 - 한 씬 안에 층을 세로로 쌓는다

층마다 씬을 따로 만들지 않았다.
**모든 층을 한 씬에 미리 지어 두고, 세로로 16칸씩 떨어뜨려 쌓았다.**

```
        4F   y = +48  ┃ ▲ ▼ ┃ ·············· [회수]
        3F   y = +32  ┃ ▲ ▼ ┃ ·············· [회수]
        2F   y = +16  ┃ ▲ ▼ ┃ ·············· [회수]
        1F   y =   0  ┃ ▲   ┃ ·············· [회수]
                       계단실               반대편 끝
```

### 왜 씬을 나누지 않았나

동행자를 따라오게 하려면 이 방법이 가장 확실하다.

| | 씬을 나눔 | 한 씬에 쌓음 |
| --- | --- | --- |
| 이동 방식 | 씬 로드 | 좌표 이동 |
| 동행 NPC | 전부 사라짐 → 최면·유지도·특성·충동을 복원해야 함 | **좌표만 옮기면 끝** |
| 경쟁자 상태 | 복원 필요 | 그대로 |
| 세션 흐름 | 13일차 씬 흐름과 이중으로 얽힘 | 영향 없음 |
| 로딩 | 있음 | 없음 |

### 위아래 층이 겹쳐 보이지 않는 이유

층 간격(16)이 카메라 세로 시야(약 9.3)보다 넉넉하게 넓다.
한 씬 안에 있지만 화면에는 항상 한 층만 보인다.

## B. 층 좌표계

`Scripts/Stage/FloorSpace.cs` — 신규

모든 층 계산의 기준이다.

| 함수 | 역할 |
| --- | --- |
| `OriginY(floor)` | 해당 층의 세로 원점 |
| `FloorAt(y)` | 세로 좌표로 몇 층인지 판정 |
| `MinYOn` / `MaxYOn` | 해당 층의 보행 구역 |
| `ClampYOn(floor, y)` | 지정한 층 안으로 가둠 |
| `ClampYNear(현재 y, 목표 y)` | 지금 선 층 안으로 가둠 |
| `ToWorld` / `ToLocal` | 1층 기준 좌표 ↔ 실제 좌표 |

1층 보행 구역 상수(`WalkMinX` 등)도 여기로 옮겼다.
기존 `SchoolHallwayPrototypeBuilder.WalkMinY` 등은 이 값을 그대로 가리키므로 호환된다.

### 테스트가 잡은 버그

처음에는 층을 가두는 함수가 **가두려는 값 자체로 층을 판정**했다.

```csharp
// 처음 작성한 방식
int floor = FloorAt(desiredY);      // ← 목표 좌표로 층을 정함
return Clamp(desiredY, MinYOn(floor), MaxYOn(floor));
```

밀침 때문에 목표 좌표가 크게 튀면 그 값이 위층으로 읽힌다.
그러면 **층을 가두는 함수가 오히려 층을 빠져나가는 통로**가 된다.

테스트에서 2층에 선 채로 큰 값을 넣었더니 5층이 나왔다.

**지금 서 있는 자리로 층을 정하도록** 고치고, 위·아래 양방향을 테스트로 고정했다.

## C. 층 구성

`Scripts/Stage/FloorPlanLogic.cs` · `FloorLayout.cs` — 신규

| | 1F | 2F | 3F | 4F |
| --- | ---: | ---: | ---: | ---: |
| NPC 수 | 10 | 12 | 14 | 16 |
| 숙련 | ○ | ○ | ○ | ○ |
| 희귀 | 1명 | ○ | ○ | ○ |
| 특별 | – | – | ○ | ○ |
| 각성 | – | – | – | ○ |
| 벽 색조 | 미색 | → | → | 푸름 |

- **난수를 쓰지 않는다.** 자리 번호와 층 번호로 등급을 정한다. 같은 층은 항상 같은 구성이라 밸런스를 읽고 조정하기 쉽다
- 1층에도 희귀 한 명을 둬서 등급 차이를 처음부터 보여 준다
- **위층일수록 정기 가치 합이 크다**는 것을 테스트로 고정했다. 이게 무너지면 올라갈 이유가 사라진다

### 배치

```
[계단실 ▲▼] ··· NPC 지그재그 배치 ··· [회수 지점]
  x = -15.6 / -12.4                    x = +16.2
```

계단은 왼쪽 끝, 회수 지점은 오른쪽 끝이다.
둘을 멀리 떼어 놓아야 **"데리고 가로지르는"** 행위가 층마다 생긴다.

NPC는 계단실을 비워 두고 배치한다. 계단으로 올라오자마자 둘러싸이지 않게 하기 위해서다.

## D. 계단

`Scripts/Core/SchoolHallwayPrototypeBuilder.cs` — 층 단위로 재구성
`Scripts/Stage/FloorStairway.cs` — 신규

### 표현

- 벽면에 문틀 + 어두운 개구부
- **계단참 5단을 층계 모양으로 쌓아** 올라가는 계단인지 내려가는 계단인지 형태로 구분
- 위에 표지판과 화살표
- **갈 수 없는 방향은 막힌 벽처럼 회색으로** 그림 (1층 하행, 4층 상행)
- 두 계단 사이 표지판에 **층수만큼 금색 눈금** (3F = 눈금 3개)

막힌 쪽을 아예 지우지 않은 이유는, 모든 층에서 계단실의 모양이 같아야 "여기가 계단실"이라는 인상이 일정하게 유지되기 때문이다.

### 도착 위치

올라가면 **위층의 하행 계단 앞**에, 내려가면 **아래층의 상행 계단 앞**에 선다.
도착하자마자 돌아가는 계단이 바로 앞에 있으므로 왕복이 자연스럽다.

## E. 층 이동

`Scripts/Stage/FloorTransitionController.cs` — 신규

### 조작

계단 앞에 서면 안내가 뜨고, **W(↑)는 위층 / S(↓)는 아래층**으로 이동한다.

닿기만 해도 넘어가게 하지 않았다.
그러면 계단 앞을 지나갈 때마다 층이 바뀌어 조작할 수 없게 된다.

이동 직후 0.45초 동안 계단 입력을 막아 왕복으로 튕기는 것을 방지한다.

### 동행자 인계

동행자는 **플레이어와의 상대 위치를 유지한 채** 함께 옮긴다.

전부 한 점에 모으면 계단 앞에서 한 덩어리로 겹쳐 보인다.
상대 간격은 절반으로 줄여서 좁은 계단 앞에서 벽을 뚫지 않게 했다.

### 경쟁자 추격

**금태양·인기남도 3.2초 뒤 계단을 타고 쫓아온다.**

층 이동이 완전한 도피가 되면 쟁탈 압박이 사라진다.
경쟁자가 데리고 있는 NPC도 함께 옮기고, 둘이 한곳에 몰리지 않도록 서로 다른 계단으로 나타나게 했다.

### 물리 몸체 주의

`transform.position`만 바꾸면 `Rigidbody2D`가 다음 물리 프레임에 이전 위치로 되돌린다.
그래서 `Rigidbody2D.position`도 함께 옮기고 속도를 0으로 만든다.

## F. 층 때문에 깨질 뻔한 곳

층을 세로로 쌓자 "모든 게 1층에 있다"는 전제를 깔고 있던 코드 세 곳이 문제가 됐다.

| 곳 | 문제 | 처리 |
| --- | --- | --- |
| **스프라이트 정렬** (`DepthSortByY`) | 정렬 범위가 ±4000이라 4층(y=48)부터는 모든 캐릭터가 같은 값으로 뭉개짐 | 자기 층 원점 기준 좌표로 환산해 정렬 |
| **카메라** (`CameraFollow2D`) | 세로 추적을 0.5배로 하므로 3층에서 화면이 층 중간에 뜸 | 층 원점 기준으로 계산한 뒤 원점을 더함 + 즉시 따라붙기 추가 |
| **NPC 방황** (`NpcAgent`) | 목적지를 1층 범위로 가둬서 위층 NPC가 1층으로 끌려 내려감 | 자기 층 범위로 가둠 |

동행 줄 세우기(`FollowerManager`, `OpponentFollowerManager`)도 같은 이유로 층 기준으로 바꿨다.

층끼리는 화면에 함께 보이지 않으므로, 서로 다른 층의 정렬 값이 겹쳐도 문제가 없다.

## H. 14일차 밸런스 자산 버그 수정

Unity Test Runner에서 7개 테스트가 실패해서 추적하다가, **14일차부터 있던 실제 버그**를 찾았다.
처음에는 별도 커밋으로 올렸으나, 커밋 목록을 정리하면서 16일차 커밋에 합쳤다.

### 원인 1 - 자산의 배열 값이 잘못된 형식으로 기록돼 있었다

`StageBalanceDatabase.asset`을 직접 작성하면서 배열 3개를 잘못된 형식으로 기록했다.

```yaml
# 잘못 기록된 것
SimultaneousMultipliers: 0100000000000000

# 올바른 형식
SimultaneousMultipliers:
- 1
- 1.2
- 1.4
- 1.7
- 2
```

| 배열 | 올바른 값 |
| --- | --- |
| 동시 회수 배율 | 1.0 / 1.2 / 1.4 / 1.7 / 2.0 |
| 체인 최면 속도 | 1.0 / 0.7 / 0.5 |
| 체인 최면 비용 | 0 / 15 / 25 |

테스트에서 확인된 증상은 이렇다.

- 2명만 동시에 회수해도 최대 배율 ×2.0
- 체인 최면 첫 대상부터 속도 절반
- 체인 비용 총합이 40이 아니라 50

즉 **14일차 이후 실제 플레이에서도 회수 배율과 체인 최면이 틀어져 있었다.**

### 원인 2 - 플레이 후 남은 값이 테스트로 새어 들어갔다

이 프로젝트는 **Enter Play Mode Options에서 도메인 리로드를 끄고 있다.**
이 설정에서는 한 번 플레이하면 자산에서 읽은 값이 static 변수에 그대로 남는다.

그 상태로 테스트를 돌리니 "자산이 없으면 코드 기본값을 쓴다"는 전제가 깨졌다.

또 `BalanceBootstrap`의 `_applied` 플래그가 true로 남아서, **두 번째 플레이부터는 자산을 다시 읽지도 않았다.**

### 수정

| 파일 | 내용 |
| --- | --- |
| `StageBalanceDatabase.asset` | 배열 3개를 올바른 형식으로 재기록 |
| `BalanceIsolationSetUp.cs` (신규) | 테스트 전체 시작 전·종료 후 주입된 값을 비움 |
| `BalanceBootstrap.cs` | `SubsystemRegistration` 시점에 먼저 비운 뒤 자산을 다시 읽음 |
| `BalanceAssetConsistencyTests.cs` (신규) | **실제 자산 파일**을 읽어 배열이 코드 기본값과 같은지, 순서가 뒤집히지 않았는지 검사 |

### 왜 그동안 잡히지 않았나

로직 테스트는 설계상 자산을 읽지 않는다 (14일차에 의도한 구조).
그래서 자산이 깨져도 로직 테스트는 전부 코드 기본값으로 통과했다.

**자산 자체를 검사하는 테스트가 없었던 것이 빈틈이었다.**
`BalanceAssetConsistencyTests`가 그 틈을 막는다. 이 테스트는 Unity가 자산을 불러와야 하므로 Test Runner에서만 돈다.

## 판단한 것

### 1. 동행 중인 NPC만 옮긴다

최면은 걸렸지만 동행 한도를 넘어 따라오지 않는 NPC는 그 층에 남는다.
여전히 플레이어 소유이고, 다시 내려가면 그 자리에 있다.

동행 한도가 이 게임의 핵심 자원이다. 층 이동으로 이걸 우회하게 두지 않았다.

### 2. 목표 정기와 제한 시간은 판 전체 공용이다

층마다 목표를 나누면 "한 층만 파먹기"가 최적 전략이 된다.
지금은 어느 층에서 모으든 같고, **위층은 효율이 좋되 경쟁자가 따라붙는** 구조다.

### 3. 첫 방문 신호만 연결해 두었다

층은 오르내릴 수 있으므로 같은 층을 여러 번 지나간다.
보상이 반복 지급되지 않도록 `FloorRunState.MoveTo`가 **처음 도달했을 때만 true**를 돌려주고,
`FloorTransitionController.FloorChanged` 이벤트로 전달한다.

이 신호를 실제로 쓰는 **런 강화 3택**은 다음 일차에서 붙인다.
