# Project θ 개발 일지 — 13일차

## 개발 목표

12일차까지 스테이지 하나는 충실히 완성됐지만, 그 스테이지를 **오가는 길이 없었다.**

13일차는 화면 흐름 골격과 세이브 기반을 만들었다.

```text
Boot ──자동──> MainMenu ──[시작]──> Hub ──[출격]──> TestStage
                  ↑                                    │
                  └────────[허브로]────── 결과 화면 ────┘
```

## 문제 인식

씬 파일은 1일차부터 `Boot` · `MainMenu` · `TestStage` 세 개가 있었고 Build Settings에도 등록돼 있었다.

그런데 실제 상태를 확인해 보니 다음과 같았다.

| 항목 | 상태 |
| --- | --- |
| `Boot` 씬 내용 | 카메라 + 빈 오브젝트 2개. 스크립트 0개 |
| `MainMenu` 씬 내용 | 카메라 + 빈 오브젝트 2개. 스크립트 0개 |
| 씬 전환 코드 | 존재하지 않음 |
| 씬 파일 최종 수정 | **2일차** |

1일차 개발일지에는 "BootLoader가 Test 씬으로 전환하도록 구성되어 있음"이라고 적혀 있었으나, **그런 스크립트는 프로젝트에 없었다.**

코드 전체에서 `SceneManager` 사용처는 단 한 곳, 그것도 현재 씬 이름을 읽는 용도뿐이었다.

```csharp
string sceneName = SceneManager.GetActiveScene().name;
if (sceneName != "Test" && sceneName != "TestStage") return;
```

즉 10일 동안 **TestStage 단일 씬 전제 위에** 모든 시스템을 쌓아 올린 상태였다.

## 왜 지금 했는가

가장 큰 이유는 `FindFirstObjectByType` 이다. 시스템끼리 서로를 찾는 이 호출이 **20군데가 넘게** 쌓여 있었고, 전부 "같은 씬 안에 다 있다"는 가정 위에 있었다.

시스템을 더 얹은 뒤에 씬을 쪼개면 그 전부를 한꺼번에 고쳐야 한다. 지금이 가장 싼 시점이었다.

두 번째 이유는 세이브다. 저장은 본질적으로 "씬을 나갈 때 쓰고 들어올 때 읽는" 것이라, 나가고 들어오는 동작 없이 먼저 만들면 반드시 다시 짜게 된다. 그래서 같은 날에 묶었다.

# A. 영속 오브젝트 — GameSession

씬을 넘어 살아남는 오브젝트를 **하나만** 만들었다.

```text
GameSession (DontDestroyOnLoad)
├─ SaveData            현재 세이브 내용
├─ PendingStageResult  스테이지 → 허브로 넘길 결과
└─ GoTo()              씬 전환
```

영속 오브젝트를 여러 개 두면 초기화 순서 문제가 바로 생기므로, 세이브·결과 전달·씬 전환을 전부 여기 하나에 모았다.

`RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`로 어느 씬에서 재생을 시작하든 자동 생성된다. 개발 중 TestStage를 직접 열고 재생해도 동작한다.

# B. 씬 전환 규칙

전환 규칙을 순수 로직으로 분리했다. 실제 로딩은 `GameSession`이 하고, `SceneFlowLogic`은 "어디서 어디로 갈 수 있는가"만 판정한다.

| 현재 씬 | 갈 수 있는 곳 |
| --- | --- |
| Boot | MainMenu (자동) |
| MainMenu | Hub |
| Hub | Stage, MainMenu |
| Stage | Hub |

규칙에 없는 전환은 경고를 남기고 무시한다. 예를 들어 **타이틀에서 스테이지로 바로 갈 수 없다.** 허브를 반드시 거친다.

2일차까지 쓰던 옛 씬 이름 `Test`도 스테이지로 계속 인정한다.

# C. 씬 로드마다 부트스트랩 실행

**이번 일차에서 가장 중요한 수정이다.**

기존 부트스트랩은 이렇게 되어 있었다.

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
private static void AutoCreatePrototype() { ... }
```

이 속성은 **런타임이 시작될 때 한 번만** 호출된다. 씬을 로드할 때마다 호출되지 않는다.

따라서 지금까지는 TestStage를 직접 열고 재생했기 때문에 문제가 없었지만, **허브에서 출격하는 순간 스테이지가 아예 구성되지 않는다.** 빈 씬만 뜬다.

이를 `SceneBootstrapRouter`로 해결했다.

```text
런타임 시작
↓
sceneLoaded 이벤트 구독
↓
최초 씬은 직접 구성 (구독 전에 이미 로드되었으므로)
↓
이후 모든 씬 로드 → 씬 이름에 맞는 부트스트랩 호출
```

각 부트스트랩은 `[RuntimeInitializeOnLoadMethod]` 대신 공개 진입점 `CreateForScene()`으로 바꿨고, 이미 구성되어 있으면 스스로 빠져나가므로 중복 호출되어도 안전하다.

결과적으로 프로젝트 전체에서 `RuntimeInitializeOnLoadMethod`는 두 곳만 남았다.

```text
GameSession           BeforeSceneLoad  (영속 오브젝트 생성)
SceneBootstrapRouter  AfterSceneLoad   (라우팅 시작)
```

## 재출격 중복 방지

스테이지 부트스트랩의 중복 검사도 강화했다. 기존에는 부트스트랩 자신만 확인했으나, 플레이어 컨트롤러 존재 여부도 함께 본다.

```csharp
if (FindFirstObjectByType<ProjectThetaPrototypeBootstrap>() != null ||
    FindFirstObjectByType<PlayerSideViewController>() != null)
{
    return;
}
```

계약 정기와 성장 레벨은 필드만 준비해 두고 14일차에 사용한다.

## 읽기 실패는 게임을 막지 않는다

`SaveSystem.Load()`는 어떤 상황에서도 유효한 데이터를 반환한다.

```text
파일 없음      → 기본값
내용이 비어 있음 → 기본값
JSON 파싱 실패  → 경고 로그 후 기본값
예외 발생      → 경고 로그 후 기본값
```

**세이브 오류로 게임이 켜지지 않는 것이 최악**이기 때문이다.

읽어들인 데이터는 `SaveDataLogic.Normalize()`를 거친다. 음수 값은 0으로, 배열 길이가 다르면 맞춰서 복사하고, 랭크 라벨이 비어 있으면 `-`로 채운다. 플레이 횟수가 클리어 횟수보다 작은 모순도 보정한다.

## 버전 필드를 처음부터

35일차에 세이브 호환성·마이그레이션 검증이 잡혀 있다. 버전 없이 시작하면 그때 마이그레이션 경로를 만들 수 없으므로 지금부터 넣었다.

아직 구버전이 없어 `Migrate()`는 버전 번호만 맞추지만, 호출 지점과 테스트를 미리 만들어 두었다. 미래 버전 파일을 만나도 현재 버전으로 다룬다.

## 기록 갱신 규칙

| 항목 | 규칙 |
| --- | --- |
| 플레이 횟수 | 클리어·실패 무관하게 증가 |
| 클리어 횟수 | 클리어한 판에만 증가 |
| 최고 점수 | 실패한 판도 갱신 가능 |
| 최고 랭크 | **클리어한 판에서만** 갱신 |

낮은 기록은 무시한다. A 랭크 이후 C 랭크로 클리어해도 최고 랭크는 A로 유지된다.

# 테스트

13일차에 추가한 EditMode 테스트는 다음과 같다.

`SceneFlowLogicTests`

- Boot는 타이틀로만 갈 수 있는지
- 타이틀에서 스테이지로 직행할 수 없는지
- 허브에서 스테이지·타이틀 양쪽으로 갈 수 있는지
- 스테이지에서 허브로만 돌아가는지
- 옛 씬 이름(`Test`)도 스테이지로 인정하는지
- 알 수 없는 씬과 None 목적지 거부
- 스테이지를 떠날 때만 저장하는지
- 목적지 → 씬 이름 매핑

`SaveDataLogicTests`

- 기본 세이브가 유효한지
- null 세이브가 기본값으로 대체되는지
- **손상된 세이브(음수·null·배열 길이 불일치)가 복구되는지**
- 플레이 횟수가 클리어 횟수보다 작아지지 않는지
- 랭크 우열 순서 (S > A > B > C > -)
- 클리어가 두 카운터를 모두 올리는지
- **실패는 플레이로만 세고 랭크는 갱신하지 않는지**
- 낮은 기록이 최고 기록을 덮지 않는지
- 더 좋은 랭크는 갱신되는지
- Clone이 독립적인지
- 마이그레이션이 항상 현재 버전으로 수렴하는지

씬 전환 자체는 Unity 런타임이 필요하므로, **전환 "규칙"만 순수 로직으로 분리해** 테스트했다.
세이브 파일 입출력도 `JsonUtility`가 네이티브 호출이라 로직 계층과 분리해 두었다.

## 13일차 결과

13일차를 기준으로 이 프로젝트는 처음으로 **"게임"의 형태**를 갖췄다.

지금까지는 Unity에서 특정 씬을 열어야만 동작하는 기능 뭉치였다면, 이제는 타이틀에서 시작해 허브를 거쳐 스테이지를 돌고 다시 돌아오는 순환이 생겼고, 그 순환이 파일에 남는다.

특히 `RuntimeInitializeOnLoadMethod`가 씬 로드마다 호출되지 않는다는 점은 흐름을 실제로 연결해 보지 않았다면 한참 뒤에야 발견했을 문제다. 씬 연결을 앞당긴 판단이 여기서 바로 값을 했다.
