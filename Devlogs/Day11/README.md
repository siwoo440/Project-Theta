# Project θ 개발 일지 — 11일차

## 개발 목표

10일차까지 "누구를 노릴까"라는 선택(NPC 등급·특성)을 만들었다.

11일차는 여기에 **"언제, 어떻게 회수할까"라는 선택**을 붙이고, 그 결과를 랭크로 돌려주는 평가 시스템을 구현했다.

```text
A. 정기를 회수 확정형으로 전환
B. 동시 회수 배율
C. 콤보 시스템
D. 점수 시스템
E. C/B/A/S 랭크
F. 결과 화면과 등장 연출
```

## 문제 인식

10일차까지 이 게임에는 "잘했다"는 개념이 없었다.

정기 200을 아슬아슬하게 채워도, 희귀 NPC만 골라 한 번에 회수해도 화면에는 똑같이 `CLEAR` 두 글자만 떴다.

더 근본적인 문제는 정기 획득 구조였다.

```text
동행 중 초당 자동 획득   ← 대부분이 여기서 들어옴
회수 지점 도착 시 보너스
```

그냥 데리고 다니기만 해도 정기가 쌓이므로, 회수 지점까지 가져가는 긴장감이 없었다.

기획서 3.2절의 핵심 원칙은 "지금 회수할지, 조금 더 욕심낼지를 계속 판단해야 한다"인데, 실제로는 **안전하게 한 명씩 나르는 것이 항상 최적**이었다. 위험을 감수해도 돌아오는 것이 없었기 때문이다.

# A. 정기를 회수 확정형으로 전환

기획서 10.1절 "정기는 최면 성공 시 즉시 획득하지 않고 회수 지점까지 데려간 뒤 확정한다"를 그대로 구현했다.

```text
기존
최면 성공 → 동행 중 초당 +1 → 회수 시 +5

변경
최면 성공 → 임시 확보(정기 0) → 회수 지점 도착 → 등급 가치 확정
```

동행 중 정기를 생산하던 `FollowerEssenceProducer`를 제거하고, 회수 시 `NpcProfile.EssenceValue`를 그대로 지급한다.

10일차에 밸런스 보호를 위해 배율로 우회했던 부분을 기획서의 절대값으로 정리했다.

이제 데리고 다니다 빼앗기면 **그 NPC 몫의 정기가 통째로 사라진다.**

## 할당량 재조정

회수만으로 정기가 들어오므로 목표치를 다시 잡았다.

현재 스테이지 구성(일반 5 / 숙련 3 / 희귀 1 / 각성 1)의 특성 보정 포함 가치는 대략 다음과 같다.

| 등급 | 기본 | 특성 보정 후 | 인원 | 합계 |
| --- | ---: | ---: | ---: | ---: |
| 일반 | 10 | 10 ~ 12 | 5 | 약 55 |
| 숙련 | 20 | 22 ~ 33 | 3 | 약 78 |
| 희귀 | 40 | 66 ~ 76 | 1 | 약 66 |
| 각성 | 50 | 98 | 1 | 약 98 |
| 합계 | | | 10 | **약 297** |

목표 정기를 200에서 **140**으로 낮췄다. 전원 회수할 필요는 없지만 절반 가까이 지켜내야 하는 수준이다.

다만 이 값은 계산상의 추정이므로, 실제 플레이 데이터를 보고 조정이 필요한 임시 기준이다.

# B. 동시 회수 배율

기획서 10.2절의 핵심 리스크·리워드다.

| 동시 회수 인원 | 배율 |
| ---: | ---: |
| 1명 | ×1.0 |
| 2명 | ×1.2 |
| 3명 | ×1.4 |
| 4명 | ×1.7 |
| 5명 이상 | ×2.0 |

## 정산 창 방식

"동시"를 어떻게 판정할지가 문제였다. 회수 지점에 동시에 겹쳐 들어오는 것을 요구하면 조작이 너무 까다롭다.

그래서 **첫 회수 시점부터 1.5초 동안 정산 창을 열고, 그 안에 들어온 NPC를 한 묶음으로 처리**하는 방식을 썼다.

```text
첫 NPC 회수
↓
정산 창 열림 (1.5초)
↓
그 사이 들어온 NPC 계속 적립
↓
창 닫힘
↓
인원수에 맞는 배율로 한꺼번에 확정
```

창은 첫 회수 시점에 열리고 이후 회수로 연장되지 않는다. 연장되면 한 명씩 천천히 넣어도 무한히 묶여 배율의 의미가 사라지기 때문이다.

제한 시간이 끝나는 순간에는 남은 묶음을 먼저 확정한 뒤 승패를 판정한다.

## 정산 진행 표시

HUD에 현재 정산 중인 인원과 배율을 실시간으로 보여준다.

```text
회수 정산 중 3명  ×1.4
```

이 표시 덕분에 "한 명 더 데려올까, 지금 넣을까"라는 판단이 실제로 성립한다.

# C. 콤보 시스템

기획서 10.3절 기준이다. 짧은 시간 안에 연속으로 성과를 내면 배율이 쌓인다.

| 적립 조건 | 비고 |
| --- | --- |
| 최면 성공 | |
| 재탈환 성공 | 최면 성공 + 재탈환으로 2회 적립 |
| 회수 확정 | |
| 2명 이상 동시 회수 | 회수 적립에 1회 추가 |
| 힘겨루기 승리 | |

- 마지막 성과로부터 **6초** 동안 아무 성과가 없으면 콤보가 끊긴다.
- 배율은 콤보 1당 +0.1, 최대 **×3.0** (콤보 20).
- **붙잡히면 콤보가 즉시 0으로 끊긴다.**

## 콤보 배율은 점수에만 적용한다

콤보 배율을 정기에 곱하지 않고 점수에만 곱했다.

정기는 클리어 조건이고 점수는 랭크 평가다. 둘을 섞으면 "클리어는 했지만 점수는 낮다"가 성립하지 않아 랭크가 무의미해진다.

# D. 점수 시스템

기획서 16.1절의 점수 요소를 구현했다.

| 요소 | 점수 |
| --- | ---: |
| 확정 회수 정기 | 정기 × 10 |
| 최대 동시 동행 인원 | 인원 × 150 |
| 최고 콤보 배율 | (배율 − 1) × 500 |
| 재탈환 | 회당 200 |
| 힘겨루기 승리 | 회당 300 |
| 고충동 NPC 무사 회수 | 회당 250 |
| 남은 제한 시간 | 초당 20 |
| 붙잡힘 | 회당 −300 |

고충동 무사 회수는 **충동 게이지 70% 이상인 NPC를 폭주시키지 않고 회수**한 경우를 말한다. 위험을 감수한 플레이에 직접 보상을 주는 항목이다.

총점은 0 아래로 내려가지 않는다.

성과 집계는 `StageScoreTracker`가 담당하고, 각 시스템은 성과가 발생한 순간 Report 계열 메서드를 호출하기만 한다.

```text
HypnosisCaster       → ReportHypnosisSuccess(재탈환 여부)
OpponentDuelController → ReportDuelWin()
StageSessionController → ReportRecovery(정기, 인원, 위험 회수, 고등급)
StageSessionController → ReportCapture()
```

# E. C/B/A/S 랭크

점수 구간으로 랭크를 매긴다.

| 랭크 | 기준 점수 |
| --- | ---: |
| C | 6,000 미만 |
| B | 6,000 이상 |
| A | 11,000 이상 |
| S | 16,000 이상 + 추가 조건 |

## S 랭크에 추가 조건을 둔 이유

S만 점수 외에 조건을 하나 더 요구한다.

```text
붙잡힘 0회
+
희귀 · 특수 · 각성 NPC 최소 1명 회수
```

점수만으로 S를 주면 **일반 NPC를 안전하게 반복 회수하는 것이 최적 전략**이 되어버린다.

그러면 기획서 16.2절의 "위험 행동과 고난도 NPC를 적극적으로 활용한 플레이"라는 S의 정의가 깨진다.

구간 값은 프로토타입 플레이 데이터를 보고 조정할 임시 기준이며, 테스트로 고정해 두었다.

# F. 결과 화면과 등장 연출

기존 `CLEAR` / `FAILED` 두 글자를 결과 패널로 교체했다.

```text
┌─────────────────────────┐
│         RANK  A         │  ← 도장처럼 찍힘
├─────────────────────────┤
│ 회수 정기      140 / 140 │  ← 딱
│ 최대 동행         6명    │  ← 딱
│ 최고 콤보       ×2.4    │  ← 딱
│ 재탈환            3회    │  ← 딱
│ 힘겨루기 승리     2회    │  ← 딱
│ 남은 시간       00:32    │  ← 딱
│ 총점           12,480   │  ← 딱
└─────────────────────────┘
```

## 등장 연출

각 항목이 **0.26초 간격으로 하나씩** 나타난다.

나타날 때는 1.45배 크기에서 시작해 0.18초에 걸쳐 원래 크기로 줄어든다. 튀어나왔다가 딱 멈추는 느낌을 만들기 위해 감속 곡선을 사용했다.

```text
scale = 1 + 0.45 × (1 − t)²
```

총점까지 모두 나온 뒤 **0.4초 쉬고** 랭크가 등장한다.

랭크는 2.6배 크기에서 시작해 0.26초에 걸쳐 내려앉는다. 도장이 찍히는 느낌을 위해 항목보다 더 가파른 곡선을 썼다.

```text
scale = 1 + 1.6 × (1 − t)³
```

동시에 알파값이 빠르게 차올라, 커다란 잔상이 순간적으로 압축되며 박히는 것처럼 보인다.

랭크 색상은 등급별로 구분한다.

```text
S  금색
A  분홍
B  하늘색
C  회백색
```

## 클릭 스킵

마우스 좌·우 클릭 중 아무거나 누르면 연출을 건너뛰고 전부 즉시 표시된다.

구현은 **경과 시간을 전체 연출 길이로 바꿔주는 것**으로 처리했다.

```text
_elapsed = GetTotalDuration(...)
```

연출 계산을 "시간을 넣으면 상태가 나오는 순수 함수"로 분리해 두었기 때문에, 스킵 처리에 별도 분기가 전혀 필요 없다. 스킵 후의 화면이 연출을 끝까지 본 화면과 반드시 동일하다는 것도 테스트로 보장된다.

전체 연출 길이는 약 2.5초다.

## 효과음

항목이 나타날 때마다 짧은 "딱" 소리를, 랭크가 찍힐 때는 묵직한 소리를 재생한다.

프로토타입 단계이므로 오디오 파일 없이 런타임에서 생성한다. `RuntimeUiSfx`로 분리해 두었고, 정식 사운드가 준비되면 호출 지점은 그대로 두고 클립만 교체하면 된다.

인기남 선점 효과음도 같은 구조를 중복 구현하고 있었으므로 이후 정리 대상으로 남겨둔다.

## Input System 관련 수정

첫 구현에서 클릭 스킵을 구 `UnityEngine.Input` API로 작성했다가 재생 중 예외가 발생했다.

```text
InvalidOperationException: You are trying to read Input using the
UnityEngine.Input class, but you have switched active Input handling
to Input System package in Player Settings.
```

이 프로젝트는 Input System 패키지를 사용하므로, 기존 입력 코드와 동일하게 전처리기 분기로 맞췄다.

```text
#if ENABLE_INPUT_SYSTEM
    Mouse.current.leftButton.wasPressedThisFrame
    Mouse.current.rightButton.wasPressedThisFrame
#else
    Input.GetMouseButtonDown(0 / 1)
#endif
```

같은 실수가 남아 있는지 스크립트 전체에서 `#if ENABLE_INPUT_SYSTEM` 가드 밖의 구 Input 호출을 전수 확인했고, 남은 곳은 없었다.

## 시간 처리

연출은 `Time.unscaledDeltaTime`을 사용한다.

스테이지 종료 시 게임 시간을 멈추는 처리가 이후에 추가되어도 결과 화면 연출은 정상 동작해야 하기 때문이다.

## 11일차 결과

11일차를 기준으로 이 게임에 처음으로 **"잘했다"는 판정**이 생겼다.

정기를 회수 지점에서만 확정하게 바꾸면서 최면 성공은 "임시 확보"로, 회수는 "확정"으로 명확히 갈렸다. 무리를 오래 끌고 다닐수록 동시 회수 배율은 커지지만 빼앗기고 폭주할 위험도 함께 커지므로, 기획서가 말하는 "지금 회수할지 조금 더 욕심낼지"의 판단이 실제 플레이에서 작동하기 시작했다.

다음 일차(최면 확장)에서 추가할 최면 파동·다중 최면·소비 아이템은 이제 "그걸 썼을 때 랭크가 어떻게 달라지는가"를 기준으로 튜닝할 수 있다.
