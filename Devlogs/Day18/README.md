# 18일차 - 통합 마감 및 전체 코드 최적화

## 이번 일차의 목표

15~17일차 사흘 동안 큰 시스템을 세 개 연달아 넣었다.

| 일차 | 넣은 것 |
| --- | --- |
| 15 | 화면 전체를 Canvas UI로 새로 만듦 |
| 16 | 복도 하나 → 4층 건물 |
| 17 | 한 판 안의 레벨·카드 |

그 사이 원래 15일차에 하기로 한 "처음부터 끝까지 이어서 확인하는 날"을 두 번 건너뛰었고,
일차마다 "다음으로 넘긴 것"이 쌓였다.

18일차는 **새 기능 없이 숙제를 닫고, 전체 코드를 최적화하고, 한 판이 끝까지 도는지 확인하는 날**이다.

16일차에 이미 한 번 겪었다. 14일차 자산 버그는 테스트가 전부 통과하는 동안 이틀 넘게 실제 플레이를 망가뜨리고 있었다.

진행 순서는 **D → 최적화 → A → B → C → E**였다.
D(전역 값 점검)를 먼저 한 이유는, 이전 판의 값이 남는 문제가 살아 있으면 나머지를 확인할 때
"방금 고친 게 문제인지, 이전 판이 남은 게 문제인지" 구분할 수 없기 때문이다.

매 프레임 도는 코드에서 비용이 큰 패턴을 전체 스크립트에서 검색했다.

**16일차에 층이 생기면서 NPC가 10명에서 52명으로 늘었는데, 코드는 10명 기준 그대로였다.**
비용이 NPC 수에 비례하거나 NPC 수의 제곱에 비례하는 곳이 5배, 27배로 불어나 있었다.

| 순위 | 위치 | 문제 | 규모 |
| ---: | --- | --- | --- |
| 1 | 최면 시전 `HypnosisCaster` | 좌클릭을 누르는 동안 **매 프레임** `FindObjectsByType`로 씬 전체 검색 + 배열 할당 | 매 프레임 52명 |
| 2 | NPC 밀어내기 `NpcSoftSeparation` | NPC마다 다른 NPC 전부와 거리 계산, 쌍마다 상대 `transform.position`을 새로 읽음 | 한 프레임 **2,704쌍** |

## 최적화 - 고친 것

### 1. 씬 검색 → 등록 목록

`HypnosisTarget`과 `OpponentControllerBase`에 **활성 목록**을 두었다.
켜질 때(`OnEnable`) 넣고 꺼질 때(`OnDisable`) 뺀다.

```csharp
// 전
HypnosisTarget[] targets = FindObjectsByType<HypnosisTarget>(FindObjectsSortMode.None);

// 후
HypnosisTarget.CopyActive(_targetBuffer);
List<HypnosisTarget> targets = _targetBuffer;
```

목록을 그대로 넘기지 않고 **호출한 쪽의 버퍼에 복사**한다.
순회 도중 NPC가 꺼지거나 켜지면 원본 목록이 바뀌어 순회가 깨지기 때문이다.
버퍼는 재사용하므로 첫 프레임 이후 할당이 없다.

**씬 검색 10곳 → 0곳.** 스테이지 종료 시 한 번만 도는 `StageEndController`는 그대로 두었다.

### 2. 밀어내기 - 프레임당 한 번만 위치 읽기

```
전: NPC 52명 × 상대 52명 = 2,704번 transform.position 읽기
후: 프레임 첫 호출에서 52번 읽어 배열에 저장 → 나머지는 배열에서 읽기
```

추가로 **세로 차이가 밀어내기 거리보다 크면 제곱근을 구하기 전에 버린다.**
다른 층 NPC는 세로로 16 이상 떨어져 있어서 전부 여기서 걸러진다.

기존 가중치 공식이 "거리가 기준 이상이면 0"이라, 먼저 걸러도 **결과가 완전히 같다.**

#### 최적화하다 생긴 틈을 막음

위치를 프레임당 한 번만 읽게 바꾸자, 그 프레임에 **새로 켜진 NPC가 한 프레임 동안 이전 위치값을 읽어 엉뚱하게 밀릴 수** 있었다.
NPC가 켜지거나 꺼지면 스냅샷을 무효로 하고, 스냅샷을 찍을 때의 인원까지만 계산하게 했다.

### 3. 머리 위 게이지 - 보이는 층만, 바뀔 때만

- **지금 층이 아닌 NPC는 계산하지 않는다.** 4층 건물이라 약 75%가 해당된다
- `SetActive`, `enabled`, `color`, 게이지 폭은 **값이 바뀔 때만** 쓴다
- 등급 색은 판 도중 안 바뀌므로 사실상 한 번만 쓰인다

지금 보이는 층은 `Scripts/Stage/FloorVisibility.cs`(신규)가 들고 있고, `FloorTransitionController`가 갱신한다.
층 이동은 `Update`에서 일어나고 게이지 갱신은 `LateUpdate`라서, **도착한 층 NPC는 같은 프레임에 바로 갱신된다.**

### 4. HUD - 값이 바뀔 때만 문자열 생성

`Scripts/UI/Framework/UiChangeKey.cs`(신규)

표시할 값을 정수 키 하나로 접어 두고, 키가 같으면 문자열 만들기를 건너뛴다.

```csharp
if (UiChangeKey.Changed(
        ref _healthKey,
        UiChangeKey.Of(_health.CurrentHealth, _health.MaximumHealth)))
{
    _healthText.text = $"체력  {_health.CurrentHealth} / {_health.MaximumHealth}";
}
```

| 표시 | 문자열을 만드는 때 |
| --- | --- |
| 남은 시간 | **1초에 한 번** |
| 체력·정기·동행 수·레벨·층 | 값이 바뀔 때 |
| 쿨다운·콤보 배율 | 소수 첫째 자리가 바뀔 때 |
| 계단 안내 | 다른 계단 앞에 설 때 |

키에 **상태 번호**를 섞어서, 같은 숫자라도 "차단 부적 1.0초"와 "파동 재사용 1.0초"가 같은 키가 되지 않게 했다.

### 5. 참조는 한 번만 찾기

`ImpulseMeter`, `NpcAwakeningAura`는 필요한 참조를 모두 찾으면 그 뒤로 확인하지 않는다.
플레이어·스테이지·폭주 조율·포획은 스테이지가 끝날 때까지 사라지지 않는다.

### 6. 정렬 - 같으면 안 씀

`DepthSortByY`는 마지막으로 적용한 정렬 값을 기억하고, 같으면 렌더러를 건드리지 않는다.
렌더러 구성이 바뀌는 `Refresh()`에서는 기억을 지워 반드시 다시 쓴다.

## D. 전역 값 점검

16일차에 **Enter Play Mode Options에서 도메인 리로드가 꺼져 있어** static 값이 플레이 사이에 남는 문제를 겪었다.
남아 있는 전역 값을 전부 찾아 분류했다.

| 분류 | 개수 |
| --- | ---: |
| 16·17일차에 이미 처리 | 10 |
| 다시 써도 되는 캐시 (런타임 생성 스프라이트 등) | 7 |
| **확인 필요** | **4** |

### 확인 결과 - 우연히 안전했다

네 곳 모두 읽어보니 **지금 당장 문제를 일으키는 곳은 없었다.**

Unity는 파괴된 오브젝트를 `== null`로 비교하면 참을 돌려준다.
그래서 파괴된 세션을 가리키고 있어도 "없음"으로 처리되어 새로 만들어졌다.

하지만 `GameSession.Instance?.GoTo(...)`처럼 쓰는 **`?.` 연산자는 이 규칙을 따르지 않는다.**
코드가 조금만 바뀌어도 파괴된 오브젝트에 접근할 수 있는 상태였다.

### 처리

아래 전역 값을 **플레이 진입 시(`SubsystemRegistration`) 명시적으로 비운다.**

| 전역 값 | 남으면 생길 수 있는 일 |
| --- | --- |
| `GameSession._instance` | 파괴된 세션을 가리킴 |
| `SceneBootstrapRouter` 구독 | 씬 로드 구독이 중복되거나 빠짐 |
| `PlayerUpgradeMultipliers.Active` | 파괴된 플레이어를 가리킴 |
| `GameAudio` 소스·클립 | 파괴된 오디오 소스를 가리킴 |
| `UiFontProvider` 캐시 | 파괴된 폰트를 가리킴 |
| `HypnosisTarget` 목록 (신규) | 지난 판 NPC가 목록에 남음 |
| `OpponentControllerBase` 목록 (신규) | 지난 판 경쟁자가 목록에 남음 |
| `NpcSoftSeparation` 목록 | 지난 판 NPC가 목록에 남음 |
| `FloorVisibility` (신규) | 지난 판의 층이 남음 |

**새로 만든 전역 값은 만드는 순간 초기화도 같이 넣는다**는 원칙을 이번에 정했다.

## A. 폭주 생존

### 정의

**폭주한 NPC가 플레이어를 붙잡지 못한 채 폭주 시간이 끝나면** 생존이다.

```
폭주 시작 → (포획 없음) → 폭주 시간 종료  =  생존
폭주 시작 → 포획됨       → 회복           =  생존 아님
폭주 시작 → 포획 실패     → 회복           =  생존 아님
```

마지막 줄은 다른 NPC가 이미 플레이어를 붙잡고 있어서 포획이 실패한 경우다.
플레이어가 피해낸 것이 아니므로 치지 않는다.

### 신호 경로

```
ImpulseMeter.UpdateRampaging (폭주 시간 종료)
  → RampageCoordinator.NotifySurvived
    → StageScoreTracker.ReportRampageSurvived
      ├→ 튜토리얼 5단계 완료
      └→ RunProgression: 경험치 +20
```

`RampageCoordinator`에 이벤트를 두고 점수 집계기가 구독하게 했다.
11일차부터 모든 행동을 점수 집계기 한 곳으로 모으는 구조를 그대로 따랐다.

### 튜토리얼 - 끝까지 닫힘

15일차부터 튜토리얼은 폭주 단계에 닿으면 "안내를 끝낸다"로 **임시로 덮어둔** 상태였다.
이제 실제로 폭주를 피해야 완료된다.

**끝까지 마치면 세이브에 기록하고, 다음 판부터는 안내를 띄우지 않는다.**

`SaveData.TutorialCompleted`를 추가했다.
예전 세이브 파일에는 이 항목이 없지만, JsonUtility가 읽을 때 `false`로 채우므로 **버전을 올리지 않고 호환된다.**

### 경험치

`XpRampageSurvived = 20`을 `StageBalanceValues`와 자산에 추가했다.

## B. 층별 경쟁자

### 문제

16일차에는 금태양·인기남이 **둘 다 1층에서 시작**했다.
연습용이어야 할 1층이 경쟁자 둘이 붙은 가장 험한 층이었다.

### 배치

`Scripts/Stage/OpponentFloorPlan.cs`(신규)

```
1F  연습      경쟁자 없음
2F  첫 경쟁   금태양 대기 → 만나면 그 뒤로 계단 추격
3F  이중 경쟁  인기남 대기 → 만나면 그 뒤로 계단 추격
4F  고가치    만난 경쟁자가 따라와 있음
```

| 경쟁자 | 성격 | 시작 층 | 이유 |
| --- | --- | --- | --- |
| 금태양 | 빠르고 공격적 | 2F | 1층에서 조작을 익히고 올라가면 처음 만남 |
| 인기남 | 느리지만 멀리서 노림 | 3F | 위층일수록 경쟁자가 한 명씩 늘어남 |

### 만난 뒤에만 추격

16일차의 "3.2초 뒤 계단으로 추격"은 유지하되, **한 번이라도 같은 층에 있었던 경쟁자만** 쫓아온다.
1층에서 2층 금태양이 3초 만에 내려오면 층별로 배치한 의미가 없다.

"만남"은 판 시작 시점과 층에 도착한 순간에 기록한다.
경쟁자는 추격으로만 층을 옮기므로(= 이미 만난 뒤) 이 두 시점이면 충분하다.

### 16일차부터 숨어 있던 문제

**인기남은 탐색 범위가 사실상 무제한(999)이다.**
그래서 다른 층 NPC까지 노렸고, 층 사이 벽에 막혀 **벽에 붙어 서 있게** 된다.

지금까지는 둘 다 1층에서 시작하고 추격으로만 층을 옮겨서 거의 드러나지 않았다.
위층에 배치하자마자 드러날 문제였다.

`OpponentControllerBase.IsOnSameFloor`를 추가하고, 두 경쟁자의 `IsTargetValid`에서 **같은 층 대상만** 인정하게 했다.
추적 중인 대상이 플레이어를 따라 다른 층으로 가면 그 순간 추적도 포기한다.

### 대기 동작 확인

경쟁자는 대상이 없을 때 **제자리에서 대기 시간만 흘린다** (플레이어 쪽으로 걷지 않는다).
위층에 배치해도 벽에 붙는 일은 없다는 것을 코드로 확인했다.

## C. 카드 수치 자산화

17일차에 만든 `RunUpgradeTable.Override` 주입 지점에 자산을 연결했다.
**이제 경험치와 카드 수치 모두 재컴파일 없이 조정한다.**

```yaml
_runUpgrades:
- Card: 0
  Category: 0
  DisplayName: 속박의 눈
  DescriptionFormat: 최면 속도 +{0}
  ValuePerStack: 0.2
  MaximumStacks: 3
  IsInteger: 0
```

### 같은 실수를 반복하지 않도록 세 번 확인했다

1. **객체 목록 형식**을 썼다. 12일차 소비 아이템이 같은 형식으로 문제없이 돌고 있다. 16일차에 깨진 것은 숫자 배열 형식이었다
2. 제 검증 환경은 자산을 못 읽으므로, **자산 문구와 코드 문구를 스크립트로 글자 하나까지 대조**했다. 8장 모두 일치. `−`(U+2212) 기호가 일반 하이픈으로 바뀌지 않은 것도 확인했다
3. 파일 앞 BOM 없음, 변경분 **58줄 추가뿐** (경험치 1줄 + 카드 57줄)

`BalanceAssetConsistencyTests`에 **카드 8장 × 7개 항목** 검사를 추가했다.
`BalanceBootstrap.Reset`에도 카드 표 초기화를 추가했다.

**6·7구간이 핵심이다.** D에서 막은 것들이 실제로 막혔는지 확인하는 방법은 이 두 구간뿐이다.

앞으로 큰 기능을 넣을 때마다 이 목록을 한 번씩 돌고, 맨 아래 기록 표에 남긴다.

## 판단한 것

### 1. 최적화는 게임 동작을 바꾸지 않는 것만 했다

"같은 결과를 더 싸게"만 했고, 결과가 달라지는 최적화(NPC AI 갱신 간격 늘리기, 다른 층 NPC 정지 등)는 하지 않았다.
다른 층 NPC도 계속 방황하고, 충동도 계속 오른다. 그건 게임 규칙이다.

### 2. 튜토리얼의 쟁탈 단계는 2층에서 닫힌다

튜토리얼 4단계는 "경쟁자에게 빼앗긴 NPC를 되찾기"다.
경쟁자를 2층부터 배치했으므로, 1층에서는 이 단계가 끝나지 않고 2층에 올라가야 닫힌다.
"1층 연습 → 2층 첫 경쟁"이라는 흐름과 맞아서 그대로 두었다.

### 3. 체감 성능은 측정하지 않았다

이번 최적화의 근거는 **호출 횟수와 할당 횟수를 코드로 센 것**이다.
실제 프레임 시간과 GC 수치는 Unity Profiler로 재야 정확하고, 제 검증 환경에서는 잴 수 없다.
